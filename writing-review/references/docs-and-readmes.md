# Docs and READMEs

## State the rule

A reference doc states the constraint as a flat rule. The mechanism and the
reasoning go in the code comment or the commit body.

```
BAD   A hostname gives the jail its own UTS information, so runj rejects it
      alongside `host: inherit`.
GOOD  Setting `host:inherit` and providing a value for `hostname` is invalid
      and is rejected by runj.
```

The doc states the constraint; the mechanism (the kernel silently overrides
inherit with new) lives in the test comment and the commit message.

Passive voice is acceptable here because it states the rule directly. Do not
humanize a plainly stated rule back into an explanatory active sentence.

Prefer the literal action a function takes: "runj returns an error" over "runj
rejects them with an error". Where a semicolon splices two related facts, use
the connective that names the relation: "have no FreeBSD equivalent so runj
returns an error".

## Write at the document's altitude

State each rule at the altitude of the document's subject, and give the
specific case its own heading.

`docs/jail-parameters.md` is a document about jail parameters in general. Its
boolean-encoding section was written entirely in terms of `allow.*`, the
booleans in front of the author at the time. The rewrite states the general
rule with `<name>` and `no<name>`, notes separately that a boolean nested under
a parent carries its negation on the child field (`allow.no<name>`), and moves
the `allow.*` material under its own `## allow.* toggles` heading.

The same pass cut `vnet=1 is "new", vnet=2 is "inherit"` down to "Enums (like
`vnet`) are passed as integers". The values belong in the code and in
`jail(8)`, not in a document about encoding.

A rule written at the wrong altitude implies the general mechanism applies only
to the one case in front of you.

## Do not re-derive the rule

After stating that a boolean parameter is keyed by name, a paragraph walked
through "sending `allow.suser` with an integer value of `0` does not disable
the super-user; the `0` is discarded". Review deleted the whole paragraph. The
rule above it already said this.

## Present tense only

Describe current behavior. No "no longer X", no "used to X". Say what the code
does today ("runj invokes the jail syscalls directly"), not what it changed
from. Tracking historical behavior in a doc adds noise.

Cut forward-looking sections too. A "## Status" section saying a future change
"will reuse it" was removed when a design doc landed.

## Rejected alternatives in the conditional

In an "Alternatives considered" section, state consequences in the conditional.
The option does not exist in the running system. The present indicative
asserts a hypothetical as fact.

```
BAD   an older entrypoint reads the cwd as the program to run and fails
GOOD  could read the cwd as the program to run and fail

BAD   a single variable scales, but it is still threaded through the environment
GOOD  a single variable would still be threaded through the environment
```

State the disqualifying property. Do not grant a merit first.

## Spec and handoff docs are self-standing

When each phase of a build is dispatched to its own independent agent, that
agent has the repo and none of the authoring conversation.

In-repo cross-references (DESIGN.md, sibling phase docs) are fine. Every
external resource must be written into the doc: repo URLs, API endpoints,
reference implementations, data-table sources. Give each doc an "External
references" section with real URLs. A doc that says "lift this from <repo>"
without the URL is useless to the agent that runs it.

## README audience

A README is for users of the software. Keep installation, operation, behavior,
security boundaries, and limitations there.

Maintainer mechanics go elsewhere: release workflow internals,
reproducible-build implementation details, and repository verification commands
belong in the Makefile, the workflow, or contributor-facing documentation,
unless a user needs them to use the project.

## Provenance and authored voice

When a repository was primarily generated by coding assistants under high-level
human direction, disclose that provenance directly. Do not turn it into a
conventional named attribution section when the commit trailers already record
the specific tools and models, and do not name particular assistants, vendors,
or humans unless asked to.

Preserve deliberate project-authored voice. An intentional warning, parody, or
literary structure may communicate the project's risk posture more clearly than
a generic disclaimer. Do not normalize it into neutral technical prose, and do
not remove it because ordinary commits and explanations avoid metaphors.

WebCLI's README replaced a named development-attribution section and detailed
release and verification instructions with a blunt vibe-coding warning modeled
on long-term hazard markers. The warning belongs: it communicates that passing
tests do not establish a coherent design or a trustworthy implementation. The
build and release mechanics stay in their executable sources.
